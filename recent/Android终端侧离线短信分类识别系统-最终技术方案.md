## 1. 课题定位与核心矛盾

### 1.1 目标用户与场景

| 维度 | 说明 |
|------|------|
| 硬件画像 | 4GB / 6GB RAM 中低端安卓机 |
| 隐私场景 | 政企、海外合规、无网/弱网、不愿短信上云的用户 |
| 核心痛点 | 垃圾短信多；关键词方案太笨；云端大模型不安全；本地大模型跑不动 |

### 1.2 要解决的核心矛盾

**严苛的端侧算力 / 内存 / 功耗限制** ↔ **高精度、高鲁棒、防误杀的语义分类需求**。

本课题的难点不在「把短信分个类」，而在「戴着镣铐跳舞」：约 **80% 精力**应投向模型压缩、端侧加速、以及高质量防误杀规则库；不以追求分类准确率上限为第一目标。

### 1.3 四大卖点（硬约束）

1. **零上云**：分词、特征、推理、规则决策全部在本机完成。
2. **无重型大模型**：不用数 GB 级 LLM，使用极度压缩的轻量 NLP。
3. **短信不出设备**：原始正文不上传；处理以内存为主，不落业务侧持久化库。
4. **防误杀**：银行验证码、快递取件码等事务短信召回率 ≥ **98%**（生死线）。

### 1.4 分类体系（锁定四类）

与课题表述严格对齐，不采用「五类」扩展体系：

| 标签 | 英文枚举 | 含义 |
|------|----------|------|
| 事务 | `TRANSACTION` | 验证码、账单、入账、物流取件、航班、密码修改确认等 |
| 广告 | `AD` | 商业营销、优惠促销、品牌推广 |
| 骚扰 | `HARASS` | 催收扰民、无关推销、反复骚扰类 |
| 诈骗 | `FRAUD` | 诱导转账、钓鱼链接、冒充公检法/客服/中奖等 |

> **说明**：若训练数据来自公开「Ham/Spam」二分类集，必须经映射规则 + 人工抽检后才能进入四分类训练，不可直接当四分类使用。

## 2. 方案总览与设计原则

### 2.1 一句话技术路线

**规则引擎绝对优先保护事务短信 + 轻量多语种四分类小模型补语义 + TFLite INT8 端侧推理 + 低置信度一律偏事务。**

### 2.2 设计原则

1. **防误杀 > 垃圾召回**：宁可漏拦一条广告，不可误拦一条验证码。
2. **一个多语种小模型常驻，不四模型并行**：内存预算不允许中/英/印地/印尼各挂一份大模型。
3. **规则词表宁缺毋滥**：禁止把单独的「转账」「余额」做成无条件事务白名单（诈骗短信同样高频出现这些词）。
4. **短信只在内存处理**：分类结果可本地展示；原始正文不写外部存储、不发起业务网络请求。
5. **真机验收为准**：模拟器与旗舰机数据不作最终依据。

### 2.3 交付形态（默认）

默认按 **课程 / 毕设可演示系统** 交付：

- 自研 Android App：引导用户设为默认短信应用，完成「收信 → 分类 → 展示」闭环；或
- 提供 **离线评测页**：导入本地测试集 JSON 批量回放，无短信权限也能产出验收报告。

若后续转为厂内预装 / 政企集成，可去掉「设为默认应用」引导，改为系统权限；Google Play 上架不作为第一阶段硬目标。

## 3. 总体架构

### 3.1 分层模块

```
┌─────────────────────────────────────────────────────────┐
│                    展示层（UI）                           │
│  四类 Tab / 单条理由 / 性能面板 / 离线评测报告            │
└───────────────────────────┬─────────────────────────────┘
                            │ 仅传枚举结果 + 理由字符串
┌───────────────────────────▼─────────────────────────────┐
│                 决策路由层（双保险）                       │
│  白名单 → 强事务正则 → 诈骗硬规则 → 模型 → 低置信兜底     │
└───────────────────────────┬─────────────────────────────┘
          ┌─────────────────┼─────────────────┐
          ▼                 ▼                 ▼
   ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
   │ 文本归一化   │   │ 规则引擎    │   │ 轻量 NLP    │
   │ NFKD/异形字  │   │ OTP/模板库  │   │ Tiny+INT8   │
   │ 谐音替换表   │   │ 诈骗硬规则  │   │ TFLite      │
   └─────────────┘   └─────────────┘   └─────────────┘
          ▲
┌─────────┴───────────────────────────────────────────────┐
│              输入层（SMS 读取 / 离线回放）                 │
│  默认短信应用路径 或 本地测试集；正文不落盘、不上云        │
└─────────────────────────────────────────────────────────┘
```

### 3.2 决策流水线（主路径）

```
新短信到达
    │
    ▼
文本归一化（去零宽、homoglyph、谐音表）
    │
    ▼
规则引擎
    ├─ 联系人白名单命中 ──────────────────► 事务
    ├─ 强 OTP / 取件码 / 高置信事务模板 ──► 事务（短路，不跑模型）
    ├─ 高危诈骗硬规则（可选提权）─────────► 诈骗（不得覆盖 OTP 短路）
    └─ 未命中
            │
            ▼
      轻量四分类模型
            ├─ confidence ≥ τ ──► 广告 / 骚扰 / 诈骗 / 事务
            └─ confidence < τ ──► 强制事务（安全兜底）
            │
            ▼
      生成可解释理由 → 本地 UI 展示
```

### 3.3 优先级表（从高到低）

| 优先级 | 机制 | 输出 |
|--------|------|------|
| P0 | 系统联系人 / 用户白名单 | 强制事务 |
| P1 | 高精确率 OTP / 取件码 / 航班等正则 | 强制事务 |
| P2 | 诈骗硬规则（与模型可并联打分） | 诈骗提权；**不得**覆盖 P0/P1 |
| P3 | 轻量模型四分类 | 四类之一 |
| P4 | 低置信度兜底 | 强制事务 |

## 4. 第一阶段：SMS 读取与输入约束

### 4.1 读取方式

**主路径（演示闭环）**：应用注册为默认短信应用，接收 `SMS_DELIVER_ACTION`，在内存中取得发件人号码与正文后立即进入分类流水线。

**评测路径（验收必备）**：App 内「离线评测」页读取本地测试集（如 `assets/eval/*.json`），不依赖真机短信权限即可输出完整指标报告。

**备选说明（非主路径）**：第三方「SMS Screening Protocol」依赖宿主短信 App 主动调用，非 Android 系统标配，本方案不作为主交付路径，仅可作附录探索。

### 4.2 服务模型

- 收到短信后由短生命周期任务或前台服务完成推理，避免 Android 8.0+ 后台限制导致中途被杀。
- Android 14+ 需正确声明 `foregroundServiceType`（按实际用途选择，如 `specialUse` / 文档允许类型，并完成对应声明）。
- 推理放在独立 `HandlerThread` / 协程调度器，主线程只更新 UI。

### 4.3 隐私与安全硬约束

| 约束 | 要求 |
|------|------|
| 网络 | 业务路径零上云；建议不申请无关 INTERNET，或即便有也禁止短信正文上传 |
| 存储 | 原始短信正文不写入私有业务数据库 / 外部存储；分类标签与理由可本地短时缓存供 UI |
| 权限最小化 | 仅申请完成演示所需的短信相关权限；引导页明确说明「全部本地处理」 |
| 日志 | 正式构建禁止打印完整短信正文 |

### 4.4 合规现实（如实说明）

Google Play 对 `READ_SMS` 等权限极严，非默认短信/电话处理应用很难过审。本课题第一阶段以 **可演示、可验收** 为准；若未来上架，需按「默认短信应用」或官方例外条款另行准备材料，不与技术主路径绑定。

## 5. 第二阶段：双保险核心算法

### 5.1 规则 / 特征引擎（生死线，优先建设）

规则层目标：**单独运行时就应撑起事务召回的大部分配额**，模型只负责补漏与细分类。

#### 5.1.1 三类本地资产（打包进 APK，可 JSON 热更新）

**A. `otp_patterns`（高精确率，事务短路）**

覆盖中 / 英 / 印地 / 印尼常见 OTP 与取件码句式，核心思想是「**业务词 + 短距离数字**」，例如：

- 中文：`验证码` / `动态密码` / `校验码` + 4–8 位数字
- 英文：`OTP` / `verification code` / `login code` + 数字
- 物流：`取件码` / `提货码` + 数字或字母数字串
- 印尼 / 印地：对应本地 OTP 关键词（需语种词表）

**B. `transaction_templates`（宁缺毋滥）**

银行入账、信用卡还款、航班变动等**高置信模板**，人工精选；禁止用过宽单关键词（如单独「转账」）强制事务。

**C. `fraud_hard_rules`（诈骗提权，不覆盖 OTP）**

例如：「公检法 + 转账」「点击链接领取 / 中奖」「安全账户 / 冻结前转账」等组合特征，用于解释与提权。

#### 5.1.2 明确禁止的规则设计

| 错误做法 | 原因 | 正确做法 |
|----------|------|----------|
| 「转账」「余额」单独白名单 | 诈骗短信同样高频 | 与 OTP/卡尾号/入账模板组合 |
| 「尊敬的客户」单独判事务 | 广告/诈骗也会用 | 不作为强事务特征 |
| 规则命中后仍跑模型再改判 | 破坏防误杀契约 | P1 命中直接短路返回事务 |

#### 5.1.3 联系人与时效白名单

- **联系人白名单**：来自系统通讯录的号码 → 强制事务。
- **时效白名单（可选增强）**：用户刚打开外卖/打车类 App 后短时间窗内，对临时配送号放行。此为增强项，不做第一阶段必达。

### 5.2 轻量 NLP 模型层

#### 5.2.1 选型结论（务实）

| 候选 | 结论 |
|------|------|
| FastText / 纯词袋 | 太轻，对抗与多语种泛化弱，可作消融基线 |
| TextCNN | 可作为备选学生结构，短文本友好 |
| DistilBERT / MobileBERT 完整版 | 未压缩时内存与时延风险高 |
| **TinyBERT-4L（或同等体量多语种学生）+ INT8** | **主选**：体积与精度折中最优 |

**体积预算目标**：

- `.tflite` 模型文件：**≤ 15–25 MB**
- 运行时 Interpreter + 词表 + 规则 + 归一化表合计 PSS 增量：**≤ 80 MB**（为 UI 留余量，总额外占用 ≤ 100 MB）

#### 5.2.2 三阶段压缩流水线

```
教师模型（训练机）          学生模型（端侧目标）
mBERT / BERT-base    ──蒸馏──►  TinyBERT-4L + 四分类头
                                    │
                              结构化剪枝
                         （注意力头 / FFN 通道）
                                    │
                           对称 INT8 PTQ
                         （必要时再做 QAT）
                                    │
                              导出 .tflite
```

要点：

1. **知识蒸馏**：温度 Softmax + 中间层迁移（按算力裁剪）；任务头直接四分类。
2. **结构化剪枝**：优先结构化而非非结构化，便于 ARM CPU GEMM 真正加速。
3. **量化**：首选全整型 INT8；INT4 在很多低端 CPU 上需频繁解量化，可能反而更慢，以真机为准。

**明确不做（控制复杂度）**：端侧 GAN 样本生成、拼音 BiGRU-CNN 双塔、未剪枝 MobileBERT-25M 直接上机。

#### 5.2.3 推理输入

- 归一化后的短文本；截断长度按短信统计分位数设定（如 128/160 subwords）。
- 分词尽量 **少分配临时字符串**（索引式 WordPiece / SentencePiece），降低 GC 抖动。

### 5.3 双保险协同策略小结

| 场景 | 行为 |
|------|------|
| 明显验证码 | 规则短路 → 事务 |
| 变形广告/诈骗 | 归一化 + 模型细分类 |
| 模型犹豫 | `confidence < τ` → 事务 |
| 规则与模型冲突 | **规则 P0/P1 永远胜出** |

## 6. 第三阶段：端侧部署与性能优化

### 6.1 推理框架

**主选：TensorFlow Lite（LiteRT）**

- 与 Android 集成成熟，工具链完整（转换、量化、benchmark）。
- 低端机验收以 **CPU INT8** 为准；NNAPI / GPU / NPU 作为可选加速，不作为及格依赖（中低端 SoC 委托质量参差不齐）。

MNN / NCNN 可作为对比实验，不作为第一交付绑定。

### 6.2 工程级内存优化

1. **mmap 加载模型**：`MappedByteBuffer` 映射 `.tflite`，避免大块 Java 堆拷贝。
2. **进程内单例 Interpreter**：禁止每条短信重新 `loadModel`。
3. **Allocation-Free 倾向的分词**：用偏移量与整数词 ID，减少中间 `String` 爆炸。
4. **内存降级**：`onTrimMemory(RUNNING_CRITICAL)` 时卸载 Interpreter，退化到纯规则通道，避免 LMK 强杀。

### 6.3 时延优化

- 规则匹配使用预编译 `Pattern`，热路径 O(命中扫描)。
- 规则已短路则 **完全跳过** 模型。
- 线程数按大核数量配置；首次推理做预热，验收统计去掉冷启动或单独标注冷/热启动。
- 全链路计时：`归一化 + 规则 +（可选）分词 + 推理 + 路由`，用 `System.nanoTime()`。

### 6.4 真机性能监测

| 指标 | 推荐量测 |
|------|----------|
| 内存 | `ActivityManager.getProcessMemoryInfo` 的 **PSS 增量**（相对未加载模型基线） |
| 时延 | 纳秒计时；报告 P50 / P95 / Max |
| 工具 | TFLite `benchmark_model` + App 内性能面板 |

测试机必须为 **4GB 或 6GB RAM 真机**（如 Helio G 系列 / 骁龙 6 系档位），模拟器无效。

## 7. 第四阶段：结果输出与可解释性

### 7.1 最小可用产品（MVP）功能

1. 四类短信列表（Tab 或筛选）。
2. 单条详情：类别 + 置信度 + **人话理由**。
3. 性能面板：最近 N 条耗时、当前 PSS 增量。
4. 离线评测：导入测试集 → 导出本地报告（CSV/JSON）。

### 7.2 可解释性（轻量版，不做重型归因）

端侧不做完整梯度/深层 Activation 回溯（费时费内存）。采用：

| 路径 | 理由生成方式 |
|------|----------------|
| 规则命中 | 「命中事务保护规则：OTP_PATTERN_CN_01（验证码+6位数字）」 |
| 诈骗硬规则 | 「命中诈骗组合特征：公检法+转账」 |
| 模型路径 | 「模型判为广告；命中关键词：优惠/点击领取；置信度 0.91」 |
| 低置信兜底 | 「语义置信度不足，为防误杀归为事务」 |

## 8. 数据集与多语种策略

### 8.1 语种范围

必达：**中文、英文、印地语、印尼语**。每种语言至少有一份**独立测试报告**。

### 8.2 数据来源建议

| 来源 | 用途 | 注意 |
|------|------|------|
| UCI SMS Spam Collection | 英文基线 | 原为二分类，需再标注/映射 |
| 多语垃圾短信公开集 / 翻译增强 | 扩大语种覆盖 | 翻译噪声需抽检 |
| 自建中文四分类集 | 主战场 | 银行/快递/广告/骚扰/诈骗模板 |
| 印地语、印尼语小规模精标集 | 出海验收 | 可小但必须独立评测 |
| 对抗变形集 | 鲁棒性 | 训练与测试严格分离 |

### 8.3 类别不平衡

真实流量中垃圾占比往往偏低。训练期可用过采样、类别权重、focal loss 等；**不要**把复杂 GAN 嵌入增强当第一阶段必做项。

### 8.4 多语种模型策略（锁定）

**一个多语种学生模型覆盖四语种**，而不是四份模型同时常驻。

- 训练：多语混合 batch + 语种均衡采样。
- 规则：各语种 OTP / 诈骗词表分文件维护。
- 评测：按语种拆分报告，禁止只用中文均值代替。

## 9. 对抗鲁棒性设计

### 9.1 攻击面

1. **字形替换（Homoglyph）**：拉丁/西里尔/希腊相似字符。
2. **中文谐音 / 拼音**：薇信、v信、weixin 等。
3. **零宽字符 / 符号插入**：词间插入 `U+200B`、无意义标点。
4. **语序轻微打乱、空格切割**。

### 9.2 防御分层

```
原始短信
  → Unicode 规范化（NFKD）+ 去零宽
  → Homoglyph 骨架映射表
  → 中文谐音 / 常见形近替换表（规则级）
  → 规则引擎
  → 轻量模型（训练含对抗样本）
```

训练期将程序化生成的变形垃圾短信加入训练集；测试对抗集**不得**与训练增强完全同分布泄露。

### 9.3 工程取舍

拼音联合神经网络（BiGRU-CNN-JE）学术效果好，但端侧内存与工程成本高。本方案采用 **规则级音形归一 + 对抗训练**，性价比更高，足以支撑课题「对抗能力」验收。

## 10. 验收标准与评测方法

### 10.1 资源占用（轻量性）

| 指标 | 及格线 | 优秀线（建议） | 测法 |
|------|--------|----------------|------|
| 运行时额外内存 | ≤ **100 MB** | ≤ 60 MB | 真机 PSS 增量 |
| 单条全链路时延 | ≤ **500 ms** | ≤ 150 ms（热启动 P95） | nanoTime；报告 P50/P95/Max |
| 测试环境 | 4GB/6GB **真机** | 同左多机型 | 禁止仅用模拟器 |

### 10.2 业务指标（准确性与安全性）

| 指标 | 及格线 | 说明 |
|------|--------|------|
| 事务召回率 | ≥ **98%** | 100 条重要事务中最多漏/误判 2 条 |
| 细分类能力 | 广告/骚扰/诈骗可区分 | 各类 Precision / Recall / F1 单独报告 |
| 安全兜底有效性 | 低置信样本不得高比例落入广告/骚扰/诈骗 | 抽检兜底路径 |

建议同时报告：

- **仅规则** 的事务召回（证明兜底层价值）
- **规则 + 模型** 的全系统事务召回（最终验收）

### 10.3 功能覆盖（完整性）

| 项 | 要求 |
|----|------|
| 全链路闭环 | 读取（或离线回放）→ 分类 → 本地展示，零上云 |
| 多语种 | 中/英/印地/印尼独立测试报告 |
| 对抗能力 | 变形样本集上仍可识别，单独章节 |
| 可解释性 | 每条拦截/分类可展示理由 |

### 10.4 推荐测试集构成

1. **事务黄金集**：验证码、银行、快递、航班、密码修改等，人工复核。
2. **细分类集**：广告 / 骚扰 / 诈骗均衡抽样。
3. **对抗集**：谐音、插符、拼音、同形字。
4. **多语种集**：四语种各一份。
5. **压力集**：超长短信、空短信、纯数字、混合脚本（印地+英文等）。

### 10.5 成功判据（一句话）

在 4GB/6GB 真机上同时满足 **内存 ≤100MB、时延 ≤500ms、事务召回 ≥98%**，且具备多语种与对抗本地评测报告，即视为课题成功。

## 12. 风险清单与规避策略

| 风险 | 影响 | 规避 |
|------|------|------|
| 事务规则过宽 | 诈骗被放行或广告误判事务 | 高精确率模式；诈骗硬规则不覆盖 OTP |
| 事务规则过窄 | 召回 <98% | 扩充 OTP/模板黄金集；低置信兜底 |
| 模型过大 | 内存破 100MB | Tiny+INT8；单模型；mmap；必要时更小 TextCNN 备胎 |
| 低端机 TFLite 冷启动慢 | 时延破 500ms | 预热；规则短路；统计热启动；减序列长度 |
| 公开数据无四分类 | 标签噪声 | 强制人工抽检与自建中文集 |
| 每语种一模型 | 内存爆炸 | **禁止**常驻多模型 |
| 依赖 Screening Protocol | 真机生态不兼容 | 默认短信应用 + 离线评测双路径 |
| Play 上架拒审 | 产品化受阻 | 第一阶段不以商店上架为硬目标 |
| 日志泄露短信 | 隐私事故 | Release 禁正文日志；无上传代码路径 |

## 13. 附录：关键伪代码与资产清单

### 13.1 路由伪代码

```kotlin
fun classifySms(sender: String, body: String): SmsDecision {
    val text = TextNormalizer.normalize(body)

    if (ContactWhitelist.contains(sender)) {
        return SmsDecision(TRANSACTION, "白名单：系统联系人")
    }

    regexEngine.matchTransaction(text)?.let { ruleId ->
        return SmsDecision(TRANSACTION, "事务保护规则：$ruleId")
    }

    // 诈骗硬规则：仅在未命中事务保护时提权
    regexEngine.matchFraud(text)?.let { ruleId ->
        return SmsDecision(FRAUD, "诈骗硬规则：$ruleId")
    }

    val pred = tinyClassifier.predict(text)
    if (pred.confidence < CONFIDENCE_TAU) {
        return SmsDecision(TRANSACTION, "低置信度兜底，防误杀")
    }
    return SmsDecision(pred.label, "模型分类，置信度=${pred.confidence}")
}
```

## 结语

本方案把课题成功标准压缩为三句可验证的话：

1. **跑得动**：4GB/6GB 真机额外内存 ≤100MB，单条 ≤500ms。  
2. **杀不错**：事务召回 ≥98%，规则优先、低置信偏事务。  
3. **闭环本地**：读取到展示全在端侧，多语种与对抗均有本地报告。

按此实施，即可在资源铁律下完成「Android 终端侧离线短信分类识别系统」的工程落地与课题验收。
