# 最终验收报告


## 一、背景与痛点

随着短信生态复杂化，营销广告、骚扰推广与验证码、物流、银行动账等事务信息高度混杂，用户对短信的快速精准区分需求日益强烈。当前主流方案存在两大核心瓶颈：

1. 重型大模型对 4GB/6GB 内存的中低端设备算力要求过高，无法部署；
2. 云端方案存在短信正文上传泄露隐私的风险，无法适配政企、海外等合规敏感场景。

针对中低端安卓机型，既能本地离线运行又能精准细分类（广告 / 事务 / 诈骗）且不误杀事务短信的轻量化方案，存在显著的技术缺口与市场刚需。

## 二、核心目标

立足中低端 Android 设备资源约束，在零上云、无重型大模型、短信不出设备的条件下，构建一套完整的端侧离线垃圾短信细分类识别系统，实现从短信读取、文本语义理解到分类结果展示及可解释性输出的全链路本地处理，打造「轻量、稳定、防误杀、高隐私」的短信管理辅助系统。

## 三、系统架构

```text
收信（短信 Provider，先落库再分类）
  → TextNormalizer（归一化）
  → RuleEngine（规则：事务保护 / 欺诈拦截）
  → ByteEncoder（字节编码）
  → LiteRtClassifier（TFLite INT8 推理）
  → DecisionRouter（INBOX / SUSPECT / REVIEW + 可解释依据）
```

关键设计：分类与处置分离；规则只保护动作（放行/复核），不篡改分类结果；低置信与超时一律走 REVIEW 兜底；永不自动删除短信。

## 四、技术指标与证据

### 4.1 全链路工程化

| 环节 | 交付证据 |
|------|----------|
| 短信读取 | `02_Android/` 源码：Receiver 先写系统 Provider，失败安全 |
| 轻量文本分类 | Byte TextCNN，Full-INT8 TFLite（101,696 B） |
| 规则/特征引擎 | `03_规则引擎/`：otp/transaction/ad/fraud/harass 规则 JSON |
| 结果可视化与解释 | App 展示分类、置信度与规则依据；SDK 返回解释字段 |
| 端到端 Pipeline | `04_训练与数据/` 提供训练源码与配置；最终模型与指标见 `01_模型/`、`05_指标报告/` |

### 4.2 细分类与多语种

- 硬性支持中文四分类：事务（TRANSACTION）/ 广告（AD）/ 骚扰（HARASS）/ 诈骗（FRAUD），另设 `NEEDS_REVIEW` 兜底。
- 架构预留英文、印地语、印尼语扩展；当前验收口径为中文。

### 4.3 五门禁（独立 Keras 中文 validation）

| 门禁 | 目标 | round-6 最佳候选 | 判定 |
|------|------|------------------|------|
| TRANSACTION Recall | ≥0.985 | 0.9568 | 未过 |
| TRANSACTION Precision | ≥0.920 | 0.9258 | 过 |
| Macro-F1 | ≥0.860 | 0.8864 | 过 |
| HARASS F1 | ≥0.800 | 0.8194 | 过 |
| FRAUD Recall | ≥0.800 | 0.8780 | 过 |

数据来源：`05_指标报告/post_training_keras_metrics.json`。
