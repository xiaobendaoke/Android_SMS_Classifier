## 0. 摘要

**一句话结论：** 我在 4GB/6GB 中低端 Android 设备上，零上云地实现了短信四分类系统（事务 / 广告 / 骚扰 / 诈骗），采用「规则保护事务 + Byte TextCNN 轻量模型 + REVIEW 兜底」的双保险架构；端到端工程已经闭环，但事务召回 ≥98% 的正式验收指标尚未宣称达标。

**我已经做到的：**

- 完整的端到端系统：短信读取 → 归一化 → 规则引擎 → 字节编码 → TFLite 推理 → 决策路由 → 可解释展示。
- Full-INT8 端侧模型（约 92–102 KB），教师 BERT 只用于蒸馏，学生 Byte TextCNN 部署在端侧。
- 一套可复现的训练实验体系：第 1–6 轮、40+ 单变量实验，每轮独立评估并记录结论。
- Android 工程闭环：SDK + Demo App + 单元测试 + Debug APK + 发布审计，全部无 `INTERNET` 权限。

**我还没有做到的：**

- 事务召回 ≥98%（当前 validation 最好成绩 0.9568）。
- 4GB/6GB 真机 PSS 与全链路时延的正式报告。
- 完整可审计的双人金标测试集。

**我的核心复盘结论：** 工程瓶颈已经打通；指标瓶颈**不在模型结构，而在标注一致性和冻结真标缺失**。第 6 轮之后我停止了盲调超参，把下一步转向标签仲裁与数据质量修复。

## 1. 课题理解与总体思路的形成

### 1.1 我理解的课题到底在要求什么

课题原文里最关键的几个约束是：

> 中低端 Android 设备资源约束，零上云、无重型大模型、短信不出设备；四分类（事务 / 广告 / 骚扰 / 诈骗）；内存 ≤100MB、时延 ≤500ms；**事务类短信召回率 ≥98% 为硬约束**。

我把它拆成四个必须同时满足的命题：

1. **不能上云**：隐私、政企合规、无网/弱网场景都要求推理必须完全本地完成。
2. **不能用大模型**：4GB/6GB 设备跑不动数亿参数的模型，必须压缩到百万级以下。
3. **不能误杀事务短信**：验证码、银行动账、物流取件码一旦被误拦，用户损失远大于漏掉一条广告。
4. **不能只给一个标签**：系统还要能解释「为什么这么分」，否则用户不敢信任自动处置。

### 1.2 我最初的技术直觉

立项时我的第一直觉很简单：训练一个四分类小模型，塞进手机里就能跑。但很快我意识到三个问题：

| 我最初的直觉 | 推演后的问题 | 我最终的想法 |
|--------------|--------------|--------------|
| 一个分类器就够 | 事务/广告边界很模糊，模型置信度不可靠，也没有解释性 | 必须是「规则 + 模型」双保险 |
| 端侧也上个小 BERT | 内存、时延、词表 OOV 都扛不住 | 端侧只放压缩后的 Byte TextCNN |
| 指标好就是好 | 合成数据、切分污染、标注噪声都会让指标骗人 | 先把数据可信度做扎实，再谈指标 |

### 1.3 从「分类器」到「双保险系统」：第一个关键设计决策

我最终的架构不是「一个模型打天下」，而是一条**有优先级的安全流水线**：

```text
收信 → 归一化 → 规则引擎（事务保护 / 欺诈拦截）
                    ↓
             Byte TextCNN 模型（语义四分类）
                    ↓
             Decision Router（INBOX / SUSPECT / REVIEW）
```

这个设计的出发点，是「防误杀优先」：

- **规则强保护事务**：OTP、银行、物流、订单、还款、运营商等高频事务模式先被规则覆盖，避免模型把它们分成广告。
- **模型补语义**：规则覆盖不到的长尾、变体、话术，由模型负责。
- **低置信一律 REVIEW**：模型和规则都拿不准时，不自动拦截，进复核箱，等用户处理。
- **分类与处置分离**：模型输出的是「类别」，路由决定的是「动作」；规则只保护动作，不篡改模型分类结果。

最后这条是我中途修正过的：早期版本里规则会直接改写分类结果，后来我改成「规则只保护 `INBOX` 动作」，因为安全放行和语义分类是两件事，混在一起会破坏可解释性，也让评测说不清到底是模型赢还是规则赢。

### 1.4 为什么端侧选 Byte TextCNN，而不是 TinyBERT / DistilBERT

我认真对比过轻量 Transformer，最后选了 Byte TextCNN，理由是一次取舍：

| 对比项 | 轻量 BERT 类 | Byte TextCNN（我选的） |
|--------|--------------|------------------------|
| 端侧内存/时延 | 仍偏重，低端机有压力 | 模型只有几十 KB 级，CPU 可跑 |
| 词表 OOV | 依赖 WordPiece 词表 | 字节级输入，天然抗 OOV |
| 对抗变形鲁棒性 | 对同音/异形字需要额外处理 | 字节编码 + 归一化后鲁棒 |
| 语义能力 | 更强 | 较弱，但交给教师蒸馏补 |

我的判断是：端侧模型的核心矛盾是「资源约束」和「防误杀」，不是「追 SOTA 语义」；语义深度可以放在教师侧，通过蒸馏传给学生。

### 1.5 教师-学生分工：BERT 只做蒸馏

教师用 `bert-base-chinese`（Recall v5 之后确定），只负责在训练时提供软标签；端侧永远只部署学生。这条路线也决定了后续实验的主线：**所有「调模型」的努力，本质都是在让小模型更接近教师的能力**。

## 2. 数据与标注：我踩过的最深的坑

这个项目我 60% 以上的时间花在数据上。回头看，数据问题比模型问题更难发现、也更致命。

### 2.1 第一次「能跑」是假象

早期版本用合成数据 + 简单切分，训练、评测都能跑通，leakage 检查也显示 PASS。但我很快意识到这套证据不可信：

- 合成数据只有 train 157 / val 13 / test 14，样本量太小，指标波动极大。
- 简单按行随机切分，会让**同一模板、同一发件人**的短信同时出现在 train 和 test 里，模型其实是在「背答案」。

### 2.2 我发现的三个数据问题

1. **切分污染（泄漏）**：template_group / sender 跨 split 出现，validation 高估了真实能力。
2. **锁定测试集被覆盖**：某次流程后 test 从 1402 条变成 1400 条且 SHA 变了，说明「冻结集」名存实亡。
3. **标注口径混乱**：旧标注里「看到银行/验证码就标事务、看到链接就标诈骗」，导致大量事务/广告、事务/诈骗边界错标。

### 2.3 我的修正：把「切分」和「冻结」做成硬门禁

针对切分污染，我把切分逻辑从「按行随机」改成**按语义连通分量**：

> 同一 `template_group`、`sender_group`、`parent_id` 或指纹特征有任一关联，就必须进同一个 split。

落地后：

- 冻结集重建为 train 11221 / validation 1402 / test 1402，泄漏门禁 PASS。
- 事务专项集预留 600 条（OTP/银行/物流/订单/还款/运营商各 100），其关联组件 1185 条全部排除出训练，防止模型提前见过答案。
- 新增 `split_assignment`、冻结 SHA、文本质量扫描，把「锁定 test 不可见」变成可验证的纪律：**门禁不过不量化、不读 test、不覆盖 Android 模型**。

### 2.4 标注口径的演进：从「关键词直觉」到「判断顺序」

我第一次写标注指南时，自己也犯了「看到关键词就打标」的毛病。后来我重写成一套**强制判断顺序**，作为所有标注工作的唯一口径：

```text
① 是不是在骗我（假身份/假奖励/要码要钱/钓鱼）      → FRAUD
② 是不是业务结果告知（账户/订单/认证/物流/运营商） → TRANSACTION
③ 是不是正规商家促销                               → AD
④ 是不是催收/灰产/成人/赌博等扰民内容              → HARASS
⑤ 其他 / 吃不准                                    → NEEDS_REVIEW
```

关键纠偏是：**看到「银行」不一定是事务，看到「链接」不一定是诈骗**；看的是整条短信的主意图。

### 2.5 AI 标注与合规边界：一次必须记住的翻车

数据量上来后，我尝试用 GLM / DeepSeek 做多模型 A/B/C 自动标注，速度快很多。但审计时发现仓库里出现了**脚本批量写入 `HUMAN_A_001`** 的记录，这是严重问题：

- AI 不是真人，不能冒充人工标注。
- 用 AI 标注数据宣称正式指标，等于伪造验收证据。

我随即把合规边界写死：

> AI 标注结果一律标记为 `PROVISIONAL_AUTOMATED_MULTI_PASS`；只有人工 A/B 独立标注 + 第三人仲裁，才能进入正式金标流程。

这也是后来所有 AI 标注实验「能用于探索、不能用于宣称」的规则来源。

### 2.6 我的复盘结论：标签边界是当前最大的瓶颈

到最后一次一致性审计，数据质量的问题被量化了：

- AI 仲裁只覆盖了 12623 行冻结数据中的 8.8%（1109 行）。
- 28 个模板组内部标签不一致，其中 **17 组（60.7%）集中在 HARASS 边界**（FRAUD/HARASS、AD/HARASS 等）。

这直接解释了为什么 HARASS F1 一直卡在 0.80 门禁附近——不是模型不会分骚扰，而是**训练数据的「骚扰」标签本身就是乱的**。

## 3. 模型与训练：从 bootstrap 到六轮实验的思路演进

### 3.1 第一轮认知：能跑，但远远不够

第一版学生模型是 hard-only（不蒸馏）训练，评测结果：

| 指标 | 结果 | 我的判断 |
|------|------|----------|
| Accuracy | 86.8%（TFLite 819 条） | 工程可跑 |
| Macro-F1 | 81.3% | 尚可 |
| TRANSACTION Recall | 89.8% | **离 98% 差很远** |
| 量化 | hybrid_fallback | 不是严格 Full-INT8 |

当时我的结论是：模型能接进 App，但**不能宣称任何正式指标**。这让我开始认真对待「蒸馏」这条路。

### 3.2 第二轮认知：真蒸馏没有带来质变

我假设「之前没蒸馏所以不行」，于是跑通 BERT teacher → 学生蒸馏全链路：

- hard-only：Macro-F1 0.827
- BERT 蒸馏：Macro-F1 0.829

几乎没差别。这说明**瓶颈不在「有没有蒸馏」**，我于是把怀疑对象转向数据质量和标签质量。这是整个项目最重要的方向转折：**从调模型转向查数据**。

### 3.3 第三到第六轮：我把能想到的超参都试了一遍

为了严谨，我建立了一套「一次只改一个变量」的实验体系，每个实验都独立 Keras 评估、写 `decision.json`、不合格就标记 rejected。40+ 个实验覆盖了：

| 路线 | 代表实验 | 结果 | 我的结论 |
|------|----------|------|----------|
| 类别权重 | TXN 1.4 / 1.6 / 1.8 / 2.0、uniform、clip | 事务召回最高 0.9568，其余门禁波动 | 权重推不到 0.985 |
| 学习率 | 3e-4 / 5e-4 / 7.5e-4 | 5e-4 相对稳定，仍不达标 | 超参不是瓶颈 |
| 损失函数 | focal gamma 0/0.75/1.0、hard negative、boundary 权重 | 部分改善 FRAUD/HARASS，事务召回不动 | 损失设计改善有限 |
| 模型容量 | conv_filters 128、dense 160、embedding 48、kernel 3/6/9/12 | 指标接近但不过门禁 | 容量不是第一瓶颈 |
| 保护头 | 5-logit 保护头、保护头正权重、关闭保护头 | 全部 rejected | 结构上保护不了标签噪声 |
| 教师侧 | teacher 阈值、confidence floor、ensemble、加权蒸馏 | 0.92–0.96 区间 | 教师能力没被充分利用，但仍是数据问题 |
| 数据修正 | error relabel、carrier/repayment 专项、post-annotation 复评 | 事务召回短暂到 0.9558 | 局部修正有效，但一致性不足 |

第 6 轮（当前最佳候选）配置是：`lr=5e-4` + TXN 权重 1.8 + hard-only + 硬边界权重 1.5。

### 3.4 关键认知转变：先找瓶颈，再决定怎么改

第 5 轮之后我做了一次完整的**无原文错误聚类分析**，结论是：

> 硬错误集中在 TRANSACTION 与 AD / TRANSACTION 与 FRAUD 的边界上；这些错误很多不是模型「学不会」，而是**标签本身在边界上互相矛盾**。

随后的一致性审计进一步证明了这一点（HARASS 边界 17/28 组不一致）。我把下一步从「继续调参」改成了「仲裁标签」，并设计了无原文仲裁包方案（只传 ID + 哈希 + 聚合统计，不传短信正文）。

### 3.5 实验纪律：为什么我敢说这些数字是真的

为了让「指标」可信，我给自己立了几条硬规矩：

1. **validation-only**：所有调参只在 validation 上进行，locked test 全程不读。
2. **独立评估**：训练完必须用独立 Keras 评估，不能直接用训练日志的数字。
3. **一次一变量**：每个实验只改一个因素，否则说不清是谁起的作用。
4. **每个结论落盘**：`decision.json` 记录门禁结果和 rejected 原因，提交进 git。
5. **checkpoint 选择改进**：从「只追最差门禁缺口」改成「几何均值评分 + NaN 检测」，避免为了单项指标牺牲整体。

### 3.6 第 6 轮：目前最好的 rejected 候选

| 门禁 | 目标 | 第 6 轮 validation | 判定 |
|------|------|--------------------|------|
| TRANSACTION Recall | ≥0.985 | **0.9568** | 未过 |
| TRANSACTION Precision | ≥0.920 | 0.9258 | 过 |
| Macro-F1 | ≥0.860 | 0.8864 | 过 |
| HARASS F1 | ≥0.800 | 0.8194 | 过 |
| FRAUD Recall | ≥0.800 | 0.8780 | 过 |

只有事务召回一项没过。我把它完整接入了工程链（剪枝回退 → Full-INT8 101,696 B → verify → Android 资产 → APK → 审计），但明确标记为 **NOT ACCEPTED**：工程闭环归工程闭环，验收达标归验收达标。

### 3.7 我的复盘结论

40+ 个实验把事务召回从 0.89 推到 0.9568，但所有超参路线都到不了 0.985。这本身就是一个有价值的结论：

> 在标签边界不一致的数据上，任何模型结构、损失函数、超参调优都有天花板；下一步的收益在数据侧（仲裁 + 金标），不在模型侧。

## 4. 端侧工程与 Android 闭环

### 4.1 从模型到 App：SDK 推理链

我把推理封装成可复用 SDK，App 只做表现层：

```text
TextNormalizer（归一化）→ RuleEngine（规则）→ ByteEncoder（字节编码）
→ LiteRtClassifier（TFLite 反射加载，JVM 单测无需 native 库）
→ DecisionRouter（分类 + 动作）
```

这保证了「换模型不换代码」，也让 JVM 单元测试可以脱离真机运行。

### 4.2 默认短信角色与失败安全

这是一个「手机短信 App」，所以我按系统要求实现了默认短信角色相关能力：

- **先写系统 Provider，再分类**：短信先落库，分类失败也不丢消息。
- **500ms 超时 → REVIEW**：本地分类超过预算就进复核箱，而不是猜一个类别。
- **幂等投递**：重复广播用 `deliverKey` 去重。
- **锁屏隐私**：通知 `VISIBILITY_PRIVATE`，锁屏只显示脱敏摘要。
- **可恢复**：SUSPECT / REVIEW 可一键恢复到收件箱，**永不自动删除短信**。

### 4.3 合规设计：无 INTERNET、正文不出设备

- App / SDK 不申请 `INTERNET` 权限，由 `tools/check_no_network_permission.py` 强制检查。
- 正文只在内存处理，Room 只存 URI/ID 和分类元数据。
- 训练可以联网下载权重，但运行时分类绝不联网。

### 4.4 压缩链路：剪枝回退、Full-INT8、验证、导出

压缩不是「跑一次就完事」，我把它做成了带门禁的链路：

```text
代表集生成 → 结构化剪枝（预算 0.25/0.15/0.10，超精度预算则 DENSE_FALLBACK）
→ INT8 PTQ（记录 full_integer_int8 / hybrid）→ Keras-TFLite 一致性 ≥99%
→ export_android_assets（模型 + metadata + 规则）→ APK
```

值得强调的是：剪枝预算全部超限时，我允许 dense 模型前传完成量化验证，但**明确标注「不是生产剪枝验收」**；量化也区分 hybrid 与 full INT8，绝不用一个含糊的「量化过了」带过。

### 4.5 工程闭环状态（结题口径）

| 项 | 状态 |
|----|------|
| SDK 推理链 | 完成 |
| 无 `INTERNET` 权限 | PASS（13 个 Manifest 0 命中） |
| Full-INT8 TFLite | 完成（约 92–102 KB，SHA 已记录） |
| Android JVM 测试 | 22 通过 / 0 失败 |
| Debug APK | 已构建（约 32 MB） |
| 发布审计 | `PASS_ENGINEERING`（非正式验收） |
| 历史产物归档 | `recent/prior_training/` |

## 5. 成果与未宣称项（结题口径）

### 5.1 成果清单

1. **端侧可部署的完整系统**：短信读取、四分类、处置路由、解释展示全链路本地运行。
2. **可复用 SDK**：归一化、规则、字节编码、TFLite 推理、决策路由封装成 AAR。
3. **训练/压缩流水线**：教师蒸馏、学生训练、结构化剪枝、Full-INT8 量化、一致性验证、Android 资产导出。
4. **可复现实验资产**：6 轮候选 + 40+ 单变量实验，全部有独立评估与 `decision.json`。
5. **数据治理工具链**：连通分量切分、泄漏门禁、冻结集 SHA、文本质量扫描、盲审标注包。
6. **合规体系**：无网络权限检查、敏感日志检查、模型算子检查、SBOM。

### 5.2 指标现状（必须按口径表述）

所有当前指标都来自 **provisional AI 标注的 validation-only 数据**，不是正式冻结真标：

| 指标 | 第 6 轮结果 | 状态 |
|------|------------|------|

### 5.3 为什么我不能宣称事务召回 ≥98%

1. 训练和评测数据是 AI provisional 标注，不是正式双人金标。
2. 事务召回最好成绩 0.9568，离 0.985 还有真实差距。
3. 没有 4GB/6GB 真机 PSS 与时延报告，≤100MB / ≤500ms 无法宣称。
4. locked test 按纪律从未读取，因此**没有任何基于正式冻结真标集的验收结论**。

> 工程闭环（`PASS_ENGINEERING`）与业务验收（≥98% 等硬指标）是两件事；我在文档里用 `NOT_ACCEPTED`、`claim_allowed=false` 这类标记，就是为了让这两件事永远不被混淆。

## 6. 关键教训与答辩要点

### 6.1 五条最值得说的教训

**1. 指标可信比指标好看更重要。**
数据泄漏、锁定集被覆盖、默认评规则而不是评 TFLite，都会让「指标」失真。我最终把「冻结集 SHA、test 不可读、独立评估、decision.json」做成硬纪律，才敢说数字是真的。

**2. AI 标注不能冒充人工。**
自动标注速度快，但必须与人工金标严格区分；任何「AI 写 HUMAN」的行为都是验收红线。

**3. 先找瓶颈，再决定怎么改。**
40+ 个超参实验证明：在标签边界不一致的数据上，模型侧调优有天花板。错误聚类 + 一致性审计帮我找到了真正瓶颈，省下了继续盲调的时间。

**4. 实验要可复现、要留痕。**
一次一变量、独立评估、每次实验一个提交，让「这个方向试过、为什么 rejected」变成项目资产，而不是口头记忆。

**5. 工程闭环 ≠ 验收达标。**
模型接进 App、APK 能装、审计 PASS，只能证明「系统是完整的」，不能证明「指标是达标的」。两个结论必须分开写、分开宣。

### 6.2 评审可能问的问题与我的回答

**Q1：为什么事务召回一直到不了 98%？**
答：从实验结果看，瓶颈是标签一致性而非模型容量。一致性审计发现 28 个模板组内部标签矛盾、60.7% 集中在 HARASS 边界；在边界错标数据上，权重、损失、保护头都只能把事务召回推到 0.9568。下一步是仲裁这批边界标签后用干净数据重训。

**Q2：你用 AI 标注，怎么保证数据可信？**
答：AI 标注全部标记为 provisional，只用于探索性实验；正式金标必须是人工 A/B 独立标注 + 第三人仲裁 + 完整溯源（指南 SHA、时间戳、实名映射）。当前还没到正式金标冻结这一步，所以我不宣称任何正式指标。

**Q3：内存 100MB、时延 500ms 怎么保证？**
答：端侧模型压缩到约 100KB，接收链路有 500ms 超时预算，超时走 REVIEW 兜底；但真机 PSS 与 p50/p95 报告还没完成，这是验收前必须补的真机实验。

**Q4：规则和模型谁说了算？**
答：分类与处置分离。模型给出四分类语义，规则只保护事务动作（放行）和欺诈处置（复核），低置信进 REVIEW；规则不篡改分类结果，保证可解释性和评测口径。

**Q5：如果让你重来一次，会怎么优化时间分配？**
答：会更早投入标签仲裁和双人金标，而不是先跑大量模型实验。数据侧的收益被证明大于模型侧。
