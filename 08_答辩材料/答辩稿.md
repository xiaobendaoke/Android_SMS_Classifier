## 0. 开场（约 1 分钟）

各位老师好。我做的课题是「Android 端侧离线短信四分类识别系统」。

一句话概括：**在 4GB/6GB 的中低端安卓手机上，零上云、不跑大模型、短信不出设备，用一套「规则保护事务 + Byte TextCNN 轻量模型 + REVIEW 兜底」的双保险架构，把短信分成事务、广告、骚扰、诈骗四类，并且能解释为什么这么分。**

我用了 07-14 到 08-08 大约三周多的时间，把它从一份方案文档，推进到：完整可运行的 Android Demo/SDK、Full-INT8 端侧模型、六轮共 40+ 个可复现实验、模拟器 4GB/6GB 性能证据，以及一套严格的合规与审计体系。

下面我按「我一开始怎么想的、中间遇到了什么、我改了什么、现在做到哪一步、还差什么」来讲。

## 1. 我是怎么理解这个课题的

课题的约束里有四个词是我反复划重点的：

1. **中低端设备**：4GB/6GB 内存，意味着端侧模型必须很小、很省内存。
2. **零上云、无重型大模型**：隐私合规场景（政企、海外）不允许短信正文上传，也不允许跑数亿参数的大模型。
3. **防误杀**：事务短信（验证码、银行动账、物流取件码）一旦被误拦，用户损失远大于漏掉一条广告；所以事务召回 ≥98% 是硬指标。
4. **可解释**：系统不能只给一个标签，还要告诉用户「为什么」，否则用户不敢信任自动处置。

我把课题拆成了四个必须同时成立的命题：不上云、不重、不误杀、可解释。

我的第一直觉是「训练一个四分类小模型塞进手机就行」，但很快推翻了它，因为它回答不了三个问题：事务/广告边界这么模糊，一个黑盒分类器怎么保证不误杀？端侧模型怎么解释？词表外的变形话术怎么办？

所以我把目标从「做一个分类器」改成了「做一条有优先级的安全流水线」。

## 2. 总体思路与第一个关键架构决策

最终架构是一条端到端流水线：

```text
收信（短信 Provider，先落库再分类）
  → TextNormalizer（归一化：NFKC、零宽字符、混淆字）
  → RuleEngine（规则：事务保护 / 欺诈拦截）
  → ByteEncoder（UTF-8 字节编码，512 位）
  → LiteRtClassifier（TFLite INT8 推理）
  → DecisionRouter（INBOX / SUSPECT / REVIEW + 解释依据）
```

这条流水线背后的三个设计原则：

**原则一：规则和模型双保险。** 规则负责高频、确定性高的事务模式（OTP、银行、物流、订单、还款、运营商）和欺诈特征；模型负责长尾、变体、话术。规则保证不误杀，模型保证覆盖面。

**原则二：分类与处置分离。** 这是我在中途修正过的关键点。早期版本里规则会直接改写分类结果，后来我改成：模型输出「类别」，路由决定「动作」，规则只保护动作（比如事务短信强制放行进收件箱），不篡改模型分类。这样评测说得清到底是模型赢还是规则赢，可解释性也不会被破坏。

**原则三：低置信一律 REVIEW。** 模型和规则都拿不准时，不猜，进复核箱；接收链路还有 500ms 超时，超时也走 REVIEW，而不是随便给个标签。系统永远不会自动删除短信，SUSPECT/REVIEW 都可以一键恢复。

**为什么端侧选 Byte TextCNN，而不是 TinyBERT / DistilBERT？**

| 对比项 | 轻量 BERT 类 | Byte TextCNN（我选的） |
|--------|--------------|------------------------|
| 端侧内存/时延 | 仍偏重，低端机有压力 | 模型只有几十 KB 级，CPU 可跑 |
| 词表 OOV | 依赖 WordPiece 词表 | 字节级输入，天然抗 OOV |
| 变形鲁棒性 | 需额外处理同音/异形字 | 字节编码 + 归一化后鲁棒 |
| 语义能力 | 更强 | 较弱，但用教师蒸馏补 |

我的判断是：端侧模型的核心矛盾是「资源约束」和「防误杀」，不是「追 SOTA 语义」；语义深度放在教师侧，通过蒸馏传给学生。教师用 BERT，只做训练时提供软标签，端侧永远只部署学生。

## 3. 数据与标注：我踩过的最深的坑

这个项目我 60% 以上的时间花在数据上。回头看，数据问题比模型问题更难发现、也更致命。

**第一次「能跑」是假象。** 早期版本用合成数据 + 简单按行随机切分，训练、评测都能跑通，leakage 检查也显示 PASS。但我很快发现证据不可信：

- 样本量太小，指标波动极大；
- 同一模板、同一发件人的短信同时出现在 train 和 test 里，模型其实在「背答案」；
- 某次流程后 test 从 1402 条变成 1400 条且 SHA 变了，「冻结集」名存实亡。

**我的修正：把「切分」和「冻结」做成硬门禁。**

- 切分从「按行随机」改成**按语义连通分量**：同一 `template_group`、`sender_group`、`parent_id` 或指纹特征有关联，就必须进同一个 split。
- 增加 `split_assignment`、冻结 SHA、文本质量扫描，把「锁定 test 不可见」变成可验证纪律：**门禁不过不量化、不读 test、不覆盖 Android 模型。**

**标注口径的演进。** 我第一次写标注指南时自己也犯了「看到关键词就打标」的毛病。后来我重写成一套**强制判断顺序**，作为所有标注工作的唯一口径：

```text
① 是不是在骗我（假身份/假奖励/要码要钱/钓鱼）      → FRAUD
② 是不是业务结果告知（账户/订单/认证/物流/运营商） → TRANSACTION
③ 是不是正规商家促销                               → AD
④ 是不是催收/灰产/成人/赌博等扰民内容              → HARASS
⑤ 其他 / 吃不准                                    → NEEDS_REVIEW
```

关键纠偏：**看到「银行」不一定是事务，看到「链接」不一定是诈骗**；看整条短信的主意图。

**一次必须记住的翻车。** 数据量上来后我尝试用大模型做多模型 A/B/C 自动标注，速度快很多，但审计时发现仓库里出现了脚本批量写入 `HUMAN_A_001` 的记录。AI 不是真人，不能冒充人工标注；用 AI 标注数据宣称正式指标，等于伪造验收证据。我随即把合规边界写死：

> AI 标注结果一律标记为 `PROVISIONAL_AUTOMATED_MULTI_PASS`；只有人工 A/B 独立标注 + 第三人仲裁，才能进入正式金标流程。

**事务专项集。** 为了专门测事务召回，我预留了 600 条事务专项集（OTP/银行/物流/订单/还款/运营商各 100），并把关联组件 1185 条全部排除出训练，防止模型提前见过答案。

**复盘结论：标签边界是当前最大的瓶颈。** 一致性审计发现：AI 仲裁只覆盖了冻结数据的 8.8%（1109 行）；28 个模板组内部标签不一致，其中 17 组（60.7%）集中在 HARASS 边界。这直接解释了为什么 HARASS F1 一直卡在 0.80 门禁附近——不是模型不会分骚扰，而是训练数据的「骚扰」标签本身是乱的。

## 4. 模型与训练：从 bootstrap 到六轮实验的思路演进

**第一轮认知：能跑，但远远不够。** 第一版学生模型 hard-only 训练，TFLite 评测事务召回 89.8%，离 98% 差很远；量化还是 hybrid，不是严格 Full-INT8。我的结论：模型能接进 App，但绝对不能宣称任何正式指标。

**第二轮认知：真蒸馏没有带来质变。** 我假设「之前没蒸馏所以不行」，跑通 BERT teacher → 学生蒸馏全链路：hard-only Macro-F1 0.827，蒸馏 0.829，几乎没差别。这说明瓶颈不在「有没有蒸馏」。这是整个项目最重要的方向转折：**从调模型转向查数据。**

**第三到第六轮：我把能想到的超参都试了一遍。** 我建立「一次只改一个变量」的实验体系，每个实验独立 Keras 评估、写 `decision.json`、不合格就标记 rejected。40+ 个实验覆盖：

| 路线 | 代表实验 | 我的结论 |
|------|----------|----------|
| 类别权重 | TXN 1.4/1.6/1.8/2.0、uniform、clip | 权重推不到 0.985 |
| 学习率 | 3e-4 / 5e-4 / 7.5e-4 | 5e-4 相对稳定，仍不达标 |
| 损失函数 | focal gamma、hard negative、boundary 权重 | 部分改善 FRAUD/HARASS，事务召回不动 |
| 模型容量 | conv_filters 128、dense 160、embedding 48、kernel 3/6/9/12 | 指标接近但不过门禁 |
| 保护头 | 5-logit 保护头、正权重、关闭保护头 | 全部 rejected |
| 教师侧 | teacher 阈值、confidence floor、ensemble、加权蒸馏 | 0.92–0.96 区间 |
| 数据修正 | error relabel、carrier/repayment 专项、post-annotation 复评 | 局部修正有效，但一致性不足 |

第 6 轮（当前最佳候选）配置是：`lr=5e-4` + TXN 权重 1.8 + hard-only + 硬边界权重 1.5。它把事务召回推到了 0.9568，但**依然没有过 0.985**。

**关键认知转变：先找瓶颈，再决定怎么改。** 第 5 轮之后我做了无原文错误聚类分析，结论是硬错误集中在 TRANSACTION 与 AD、TRANSACTION 与 FRAUD 的边界上；这些错误很多不是模型「学不会」，而是标签本身在边界上互相矛盾。我把下一步从「继续调参」改成了「仲裁标签」。

**实验纪律：为什么我敢说这些数字是真的。** 我给项目立了几条硬规矩：validation-only（locked test 全程不读）、独立 Keras 评估（不直接用训练日志）、一次一变量、每个结论落盘 `decision.json`、checkpoint 选择用几何均值评分 + NaN 检测。

## 5. 端侧工程与 Android 闭环

**从模型到 App：SDK 推理链。** 我把推理封装成可复用 SDK，App 只做表现层：`TextNormalizer → RuleEngine → ByteEncoder → LiteRtClassifier → DecisionRouter`。这保证了换模型不换代码，也让 JVM 单元测试可以脱离真机运行。

**默认短信角色与失败安全。** 这是「手机短信 App」，所以按系统要求实现了默认短信角色相关能力：

- 先写系统 Provider 再分类，分类失败也不丢消息；
- 500ms 超时 → REVIEW，不猜类别；
- 重复广播用 `deliverKey` 去重；
- 通知锁屏隐私，只显示脱敏摘要；
- SUSPECT/REVIEW 可一键恢复，永不自动删除短信。

**合规设计：无 INTERNET、正文不出设备。** App/SDK 不申请 `INTERNET` 权限，由 `tools/check_no_network_permission.py` 强制检查；正文只在内存处理，Room 只存 URI/ID 和分类元数据；运行时分类绝不联网。

**压缩链路。** 我把压缩做成带门禁的链路：代表集生成 → 结构化剪枝（预算 0.25/0.15/0.10，超精度预算则 `DENSE_FALLBACK` 并明确标注）→ INT8 PTQ（记录 `full_integer_int8`）→ Keras-TFLite 一致性 ≥99% → 导出 Android 资产 → APK。最终 Full-INT8 模型 101,696 B（约 99KB），Keras/TFLite 一致性 0.9964。

**工程闭环状态：**

| 项 | 状态 |
|----|------|
| SDK 推理链 | 完成 |
| 无 `INTERNET` 权限 | PASS（13 个 Manifest 0 命中） |
| Full-INT8 TFLite | 完成（约 99KB，SHA 已记录） |
| Android JVM 测试 | 22 通过 / 0 失败 |
| Debug APK | 已构建（约 32MB） |
| 发布审计 | `PASS_ENGINEERING`（非正式验收） |

## 6. 收尾阶段的完整闭环尝试（07-14 → 08-08）

为了让正式验收能成立，我按「数据可信 → 干净重训 → 性能证据」推进：

1. **AI 双盲标注**：在 WSL 里用 MiniMax M3 通过 opencode 做 Pass A/B 双盲标注，Pass C 仲裁；1080 条盲包，A/B 有效配对 1039，一致率约 84.5%，Kappa 0.709，189 条冲突送仲裁。
2. **用户终审**：生成 189 行终审表，由我逐条给出 `final_label`，结果标记为 `USER_REVIEWED_AI_DUAL_PASS`，locked test 字节级不变。
3. **干净数据重训**：用用户终审数据按第 6 轮最佳配置重训，五项独立 Keras 评估结果：TXN Recall 0.884、Precision 0.910、Macro-F1 0.853、HARASS F1 0.783、FRAUD Recall 0.878，四项未过。
4. **错误聚类与扩仲裁**：无正文错误聚类确认事务/广告、骚扰/诈骗边界是主要错类；我准备了 1890 行扩仲裁包（把 zh frozen 覆盖从约 7% 提到 25%），随后按你的要求暂停。
5. **最终选定**：按你的决定，采用 round-6 最佳候选作为交付版本。
6. **4GB/6GB 模拟器性能**：新建 6GB AVD（`hw.ramSize=6144`），复用 4GB AVD，各跑 500 条样本的仪器化 PSS/时延测试：

## 9. 答辩问答库（15 题）

**Q1：为什么事务召回一直到不了 98%？**
答：从 40+ 实验看，瓶颈是标签一致性而非模型容量。一致性审计发现 28 个模板组内部标签矛盾，60.7% 集中在 HARASS 边界；在边界错标数据上，权重、损失、保护头都只能把事务召回推到 0.9568。下一步是仲裁这批边界标签后用干净数据重训。

**Q2：你用 AI 标注，怎么保证数据可信？**
答：AI 标注全部标记为 provisional，只用于探索性实验；正式金标必须是人工 A/B 独立标注 + 第三人仲裁 + 完整溯源（指南 SHA、时间戳、标注者映射）。当前还没到正式金标冻结这一步，所以我不宣称任何正式指标。用户终审的 189 行已标记为 `USER_REVIEWED_AI_DUAL_PASS`，但不能把「部分终审」冒充「完整双人金标」。

**Q3：为什么选 Byte TextCNN，不选更轻量的 Transformer？**
答：端侧模型的核心矛盾是资源约束和防误杀。Byte TextCNN 几十 KB 级、CPU 可跑、字节输入天然抗 OOV；语义深度交给 BERT 教师蒸馏补充。评测也证明在标签噪声下，模型容量不是第一瓶颈。

**Q4：规则和模型谁说了算？**
答：分类与处置分离。模型输出四分类语义，规则只保护动作（事务放行、欺诈复核），低置信进 REVIEW；规则不篡改分类结果，保证可解释性和评测口径。

**Q5：内存 100MB、时延 500ms 怎么保证？**
答：模型压缩到约 99KB，接收链路有 500ms 超时预算，超时走 REVIEW 兜底。模拟器 4GB/6GB 实测 p99 3.6ms / 93.4ms，PSS 37.9–59.5MB / 38.3–44.2MB，都在预算内；但这是工程证据，真机正式报告还没完成，验收前必须补。

**Q6：INT8 量化损失多少？**
答：Keras/TFLite 一致性 0.9964（≥0.99 通过）。INT8 评测的绝对门禁仍未过（事务召回 0.9536），这是 NOT ACCEPTED 候选的预期结果，我没有用「量化通过」模糊掉「门禁未过」。

**Q7：怎么防止数据泄漏？**
答：切分按语义连通分量（template_group/sender_group/parent_id/指纹关联必须同 split）；冻结集 SHA 入库；locked test 门禁不过不读取、不评估、不导出。这套纪律让指标可信。

**Q8：40+ 实验都没过，是不是方法有问题？**
答：正因为有「一次一变量 + 独立评估 + decision.json」的纪律，我才能证明不是方法没试够，而是数据侧瓶颈：权重、学习率、损失、容量、保护头全部到不了 0.985。这个否定性结论本身就是成果。

**Q9：为什么不宣称正式验收？**
答：三个硬缺口：事务召回 0.9568 < 0.985；没有 4GB/6GB 真机正式性能报告；没有双人金标测试集。locked test 从未读取。工程闭环与业务验收是两件事，必须分开宣。

**Q10：如果重来一次，时间分配怎么改？**
答：更早投入标签仲裁和双人金标，而不是先跑大量模型实验。数据侧的收益被证明大于模型侧。

**Q11：多语种怎么扩展？**
答：字节编码无词表 OOV，天然支持多语种；OTP 等规则已覆盖中/英/印地/印尼。英文/印地/印尼当前不是验收口径，后续补标注与分语种评测即可扩展。

**Q12：系统会不会误删用户短信？**
答：不会。短信先落库，分类失败也不丢；SUSPECT/REVIEW 可一键恢复；系统永不自动删除短信，只做分类与路由。

**Q13：离线与隐私怎么保证？**
答：App/SDK 无 `INTERNET` 权限（13 个 Manifest 0 命中），运行时零上云；正文只在内存处理，Room 只存 URI/ID 与分类元数据；隐私威胁模型与审计文档齐全。

**Q14：这个系统有没有工程实践价值与学术创新点？**
答：工程上可量产集成（SDK/AAR/APK/审计闭环）；学术上聚焦轻量模型压缩、端侧部署、可解释性、隐私合规、话术变形鲁棒性，可产出论文与专利；数据侧的「先审计标签再调模型」方法论也有价值。

**Q15：后续多久能冲过 0.985？**
答：这是工程问题不是模型问题。执行扩仲裁（覆盖 25–35%）→ 用户终审 → 干净数据重训 → 五门禁 → 真机报告。按当前标注速度，1–2 轮仲裁即可验证是否能过 0.985。
